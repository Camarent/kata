# Architecture

kata is a self-hosted learning companion. It keeps a per-user model of known topics and reads the open lesson page to mark new blocks. The core API, storage and auth serve the browser extension, the editor extension, the git hooks and the terminal tool. The trainer generates courses from concepts, saves progress and moves the mastery it records. Planning imports syllabi, triages their modules against the user's mastery, and schedules study tracks with a weekly budget and decision points. The repo holds code and docs only, no study material or personal data (`docs/design/overview.md`).

## Modules
- [config](modules/config.md) - TOML loader and env overrides; source of all settings.
- [core](modules/core.md) - Python/FastAPI HTTP API, tokens, skill-list import, job queue, concept marks, retrieval library, daily usage, per-user journal, device event ingest and message queue, policy engine, MCP server (`POST /mcp`, two read tools, egress gate), device tool in `core/kata_device/` (git pre-commit and post-commit hooks, local queue and tree-hash marker; `python -m kata_device hooks install` never overwrites a foreign hook; the `kata` entry point is not built yet), terminal tool in `core/kata_term/` (`kata term`: PTY capture of masked command lines and error kinds, JSONL spool, stdlib client; env `KATA_URL`, `KATA_TOKEN`, `KATA_TERM_MASKS`), Postgres storage, trainer (`/v1/courses`, course progress, mastery in `core/kata_core/knowledge/`, job runner `core/kata_core/jobs/runner.py`), course open link `POST /v1/courses/{id}/open` and course file serving `GET /c/{token}/{path}` (signed tokens, `core/kata_core/trainer/open_link.py`; `core/kata_core/api/routes/course_open.py:38`, `core/kata_core/api/routes/course_serve.py:55`), planning in `core/kata_core/planning/` (syllabi `/v1/syllabi`, plan `/v1/plan`, tracks and decision points `/v1/tracks`), deep health `GET /v1/health/deep` (`core/kata_core/api/routes/health.py:43`; checks DB and applied migrations, unauthenticated, booleans only), migrations CLI `core/kata_core/migrate.py` (`python -m kata_core.migrate`, `--check` lists pending and exits 1).
- [deploy](modules/deploy.md) - `deploy/`: one image `kata:${KATA_IMAGE_TAG}` built from `deploy/Dockerfile` on dev (the Python base image is pinned by digest; the Postgres and Caddy images are pinned by digest too) and shipped over SSH by `deploy/ship.sh`; the VM builds nothing (compose runs `python -m kata_core.migrate` for `migrate` and `python -m kata_core` for `core`), `deploy/compose.yaml` (migrate one-shot, then core, Postgres, Caddy on the private network, and the `reader` sandbox with no network), host config template `deploy/kata.host.toml`, small and large profiles in `deploy/env/`, backup, restore and relocation scripts, `deploy/provision-vm.sh`, systemd timer units in `deploy/systemd/`. Runbook: `docs/deployment.md`.
- [editor](modules/editor.md) - VS Code extension in `editor/`: posts one `editor.save` event per save (no document text), shows the server quiet mark as a diagnostic, runs the device hook installer on command.
- [extension](modules/extension.md) - MV3 browser extension: manifest, package, TypeScript sources in `extension/src/`; side panel lists, creates, deletes and opens courses; courses and tracks load from the backend (`panel:courses`, `panel:tracks`, `extension/src/sidepanelBoot.ts`); content bridge that gives course pages progress load and save (`extension/src/bridge.ts`, `bridgeRegister.ts`). The content script mounts the card host (`extension/src/cardHost.ts`) with the page-changed overlay, focus confirm, joke cloud and pin; the panel tab screens and their router (`extension/src/ui/panel/router.ts`) mount in `extension/src/sidepanel.ts`, and the exam entry and exam result screens are registered in `SCREENS` (`extension/src/ui/panel/screens.ts`); the Scan tab (`renderScanTab`) passes the panel's scan rows to the scan-results screen. The build has no server address: the user types the server URL in the side panel, and the origin is requested at sign-in. Marks made while the core is unreachable wait under `kata.markQueue` and flush in order.
- [reader](modules/reader.md) - sandboxed document reader (Python, `reader/`): PDF or image in, page text and clean page PNGs out, in a container with no network; spool protocol v1 with the worker (`worker/kata_worker/reader_spool.py`).
- [scripts](modules/scripts.md) - `kata_db.py` CLI: create, migrate, drop databases; `scripts/bench/` lesson-check benchmark (fake embedder, three-state accuracy and abstain rate); `scripts/dev/` gate runner `check-all.sh` and pinned browser installer `install-browsers.sh`; `scripts/deploy/` checks for the VM stack (image rules, compose and config template, tombstone replay, row counts for restore).
- [tests](modules/tests.md) - pytest suites: `tests/core` (needs Postgres; includes `test_api_health.py`, `test_migrate_cli.py`), `tests/foundation`, `tests/worker`, `tests/e2e` (full lesson loop; needs Postgres and Node), `tests/browser` (real Firefox and Chrome through selenium; only `check-all.sh --browser`), `tests/scripts` (bench, install-browsers, check-all browser mode, deploy scripts: backup, restore, relocate, provision, stack, image rules, Caddyfile).
- [tools](modules/tools.md) - quality gate definitions in `tools/gates.json`.
- [worker](modules/worker.md) - Python pull loop: takes jobs of the kinds it has handlers for (`tag`, `course.generate`, `syllabus.extract`, `scan.classify`, `scan.extract`, `quiz.generate`, `page.summary`, `reader.extract`; `worker/kata_worker/handlers/`, plus four `modelhost.*` control kinds claimed only when `[modelhost] control_enabled` is set, `worker/kata_worker/loop.py:31`), runs them through the provider router (`worker/kata_worker/providers/router.py`), which walks the `[routing]` chain per task class over the local and Anthropic providers; cloud calls pass the policy, the secret guard and the daily cost cap; reports result, output or fail. A worker on the user's GPU machine runs next to Ollama and pulls jobs over outbound HTTP as the owning user, never root, with a fixed allow-list of subcommands. Generic model names `cloud` and `local` map through `[models]` in the host config, and a literal model name in a routing chain wins. `[provider_openai]` is an OpenAI-compatible provider: base URL and token env in the host config only, an unpriced model with no cap, and its calls are logged.

Reference docs: `docs/api.md` (routes, file format, CLIs), `docs/e2e.md` (end-to-end test), `docs/decisions.md`, `docs/design/overview.md`, `docs/design/extension-ui.md` (side panel and lesson page UI design), `docs/INDEX.md` (generated file and symbol list).

## Data and control flow
1. Config: `load_config` reads `config/kata.example.toml`-shaped TOML (path from `KATA_CONFIG` or `--config`), applies `KATA_*` env overrides (`core/kata_core/config.py:111`). The `[models]`, `[provider_openai]` and `vision` keys are in the example and host files; `needs_cloud` follows the `[models]` cloud provider token (`docs/modules/core.md`).
2. Provisioning: `scripts/db/kata_db.py` calls `core/kata_core/storage/provision.py` to create databases and apply `core/migrations/*.sql`.
3. Auth: admin creates a user and an enrolment code (`core/kata_core/auth/admin.py`). Client redeems the code at `POST /auth/enrol`; the core stores only sha256 digests and returns the raw token once. Every other route takes `Authorization: Bearer`, resolved by `current_user` (`core/kata_core/api/deps.py:76`).
4. Request: route module in `core/kata_core/api/routes/` -> repository in `core/kata_core/storage/` -> Postgres. `user_id` always comes from the token.
5. Import: `POST /import` parses the skill-list text (`core/kata_core/importer/skill_list.py`) and writes topics and marks in one transaction; a bad line rejects the whole import.
6. Tagging queue: client `POST /jobs` enqueues; a worker polls `GET /jobs/next?kind=...` (204 when empty; default kind `tag`), leases a job for `lease_seconds`, and posts `result`, `output` or `fail`. Expired leases are reclaimed (`core/kata_core/jobs/queue.py`). Known/new is decided in the core from marks, not by the model.
7. Concept marks: a concept has identity (area, topic, name), unique together, and sits under a topic (`/concepts`, `core/kata_core/api/routes/concepts.py`). An alias table merges alias names into one concept. Each user marks a concept `known`, `learning` or `new` with optional evidence and dates, keyed by concept id in `concept_marks`, next to the topic-level `marks` table, which is unchanged. A block's state is derived from its concepts. Concept marks are private to their user. The concept routes also hold the definition line, an ignored list, and hard delete (`core/kata_core/api/routes/concepts.py`). The next-id call takes an id prefix, and ids are `<prefix>-<n>`.
8. Retrieval (library, no HTTP route yet): `core/kata_core/retrieval/` stores text entries (`store.py`, shared when `owner_user_id` is NULL), ranks by full-text and by cosine over embeddings, and fuses the two lists with RRF (`retriever.py`, `fusion.py`). Config `[retrieval]`; tests use the fake embedder only.
9. Lesson check: `POST /lesson-check` (`core/kata_core/api/routes/lesson_check.py:54`) returns each concept's state for the caller. A concept mark wins; otherwise the concept label is searched in retrieval and the hits decide `known`, `learning` or `abstain` (`core/kata_core/lesson_check/checker.py:40`). Thresholds in `[lesson_check]`. The check runs synchronously in the core; no worker job calls it.
9a. Scan (page classification and concept extraction): the worker runs the `scan.classify` and `scan.extract` jobs; core output hooks rewrite each job output. Routes `GET /scan/classification`, `POST /scan/choice`, `POST /scan/reassign` and `GET /scan/overview`. Page classification is cached per page, and the remembered "Which one?" pick is kept per page topic. A concept is kept only when it passes the teachable-content check. A rescan on page change keeps marks by concept id. The extension scans and rescans by concept id. The old tag job and the old extension scan still work. Page classification is checked against an evaluation set with a pass bar.
10. Cost cap (worker side): `worker/kata_worker/providers/cost.py` `capped` wraps the cloud provider in the router; it checks today's spend (`GET /usage`) before each cloud call, refuses at `cap_micro_usd`, and records the cost (`POST /usage`) after it: from the token usage the API reports, with the text-length estimate only when no usage is present. The estimate with `estimate_safety_percent` is the pre-call guard only. Local calls are not capped. A model with no pinned price is refused (`PricingError`) unless `capped(..., unpriced_ok=True)`, which runs it uncapped and logs it. Spend at or above the warn level is logged as a warning; the call still runs.
10a. Routing: the default chain per task class is `local,anthropic`; cloud is enabled by its token alone. A job that needs the cloud is refused with 409 `needs_cloud` before it is queued. Cloud calls pass the secret scanner first. Each provider has cloud policy flags per task class; a class without a cloud flag never reaches the cloud.
11. Journal and policy (library plus read route): `core/kata_core/journal/store.py` appends and pages per-user entries (`GET /v1/journal`, `core/kata_core/api/routes/journal.py:34`). `core/kata_core/policy/engine.py` turns `error`, `ok` and `idle` events into `nudge`, `stop` and `quiet_mark` decisions in memory, from `[policy]`. Device events enter at `POST /v1/events` (`core/kata_core/api/routes/events.py:100`): each event is validated (`core/kata_core/events/envelope.py`), stored once per `event_id` (`core/kata_core/events/store.py`), and only accepted ones reach the engine. The terminal tool (`kata term`, `core/kata_term/`) spools its masked command events as JSONL and posts them to the same route through its client (`core/kata_term/client.py`). Decisions become `message` rows, delivered in that response or on `GET /v1/messages` (`core/kata_core/delivery/messages.py`); each delivered message writes one journal entry. The git pre-commit hook (`core/kata_device/precommit.py`) scans the staged added lines with the shared secret scanner; a finding blocks the commit and the message names only the rule kind and file:line. A hook error lets the commit through with one warning, and CI scans again.
12. MCP: `POST /mcp` (`core/kata_core/api/routes/mcp.py:26`) takes one JSON-RPC message from an `mcp`-scoped token, dispatches it in `core/kata_core/mcp/rpc.py`, and runs each tool result through `core/kata_core/mcp/gate.py` (size, secret scan, quoting) before it is returned. Details: `docs/modules/core.md` (MCP entries).
13. Trainer: `POST /v1/courses` picks concepts (gaps or named) and queues `course.generate`; the worker posts drafts to `POST /jobs/{id}/output`; the core's output hook stores them and queues `course.build`, which the core job runner builds with the external trainer command. Progress saves (`PUT /v1/courses/{id}/progress`, compare-and-swap on revision) write evidence and move concept mastery and marks. A dojo progress import writes no evidence. Progress documents are dojo-native. A `PATCH` on the same path saves a delta of the progress document. `POST /v1/courses` refuses past `[trainer] max_courses_per_user` (0 means unlimited), and course names are unique per user. The trainer adapter `DojoTrainerCli` runs the real `dojo` CLI without a shell, runs the dojo `init` step and writes all items into one unit; trainer warnings never fail a build, only error diagnostics do. Details: `docs/modules/core.md`.
13a. Lists and tracks: named concept lists (`/v1/lists`) hold concepts and topics, and a course can be generated from a list; the list is kept. Track goals (`/v1/tracks/{id}/goals`) carry sources, progress, velocity and pace, and list the open concepts of the goal. Course regenerate replaces the course in place with a version bump and keeps a carry-over preview. A course starts at a dojo ladder rung: 0 for new, the course `learning_rung` for learning, and none when known. Dojo ladder stage 4 is learned.
13b. Course open: the side panel calls `POST /v1/courses/{id}/open` for a ready course and opens the returned signed (HMAC-SHA256) `/c/<token>/index.html` URL in a tab. The course page loads its progress through the extension bridge: page stub -> `bridge.ts` -> background (`handleBridgeMessage`) -> `progressBridge.ts` -> the progress API above. The bridge reassembles split progress parts and runs behind a `window.claude` stub. Artifact keys are relative to the course folder, and the root page is served at `GET /c/{token}/{path}`. Details: `docs/modules/core.md`, `docs/modules/extension.md`.
14. Planning: `POST /v1/syllabi` parses the syllabus text into modules and links each module to the user's concepts by label. `GET /v1/syllabi/...` and `GET /v1/plan` triage each module (known, partly known, new; action skip, skim, practice or learn) from the user's mastery, without writing. Tracks (`/v1/tracks`) hold ordered items and a deadline; `GET /v1/plan` allocates the weekly budget to the tracks earliest deadline first, and an open decision point holds its track's later items until the user decides it (`POST /v1/decision-points/{id}/decide`, journaled as `plan.decision`). Details: `docs/modules/core.md`.
15. Deployment: `deploy/compose.yaml` runs the `migrate` service (`python -m kata_core.migrate`) to completion, then the `core` service; Postgres is used by kata only; Caddy serves the private host name over TLS, and nothing is exposed to the public internet. The nightly encrypted dump (`deploy/backup.sh`, timer `deploy/systemd/`) writes a tombstone file beside it. Restore and relocation (`deploy/restore.sh`, `deploy/relocate.sh`, `--dry-run`) follow `docs/design/detailed-architecture.md` 4.3; the row-count check is `scripts/deploy/verify_counts.py`. Runbook: `docs/deployment.md`.
16. Page summary: `POST /summary` returns the cached summary for (url, text sha256) or queues `page.summary`; the worker routes the prompt under the `summary` class and posts the reply; the core's output hook cleans and caches it. `GET /summary` reads the cache.
16a. Jokes: the core-only job `jokes.fetch` fetches from a server-side source list through a hardened fetch, sanitises the text to plain text and caches it. `GET /jokes/next` and `GET /jokes/sources` read it.
17. Reader sandbox: the reader is shipped disabled. `POST /reader/documents` stores a raw PDF or image and queues `reader.extract` with the document id only. The worker fetches the bytes from core and writes them to the `reader-in` volume. The `reader` container (no network, read-only root, no secrets) parses them in a child process with limits and writes text and clean page PNGs to `reader-out`. The worker sends each page PNG to a vision model through the router (class `vision`) and posts the text; core stores text only. Only a provider with the `vision` flag (default false) gets page PNGs. Spool protocol and hardening: [reader](modules/reader.md).
18. Quiz: `POST /quiz/sources` takes an allowlisted https URL (tier 1 and tier 2 sources, each with its licence); a URL off the list, a private address or an over-long text is refused. Job kinds `quiz.fetch` and `quiz.generate` fetch the text and generate questions as strict JSON; a question whose quote is not in the fetched text, or whose stem holds an answer word, is dropped. `GET /quiz/mini` returns at most 5 questions with source, tier and licence and never an answer index. `POST /quiz/answer` runs in the core: a correct answer moves a concept from New to Learning only. Course exams stay in dojo; kata only imports their results. Exam results from dojo are imported with a confirm step; a confirmed result marks the concept Known and sends the dojo placement answer. No unconfirmed exam result marks a concept Known.
19. Review and sync: `GET /v1/review/tree` gives areas and topics with new, learning and known counts; `GET /v1/review/concepts` lists concepts filtered by name, state and `ids`, and sorts them by name, added date, last viewed or relevance. The side panel shows the pending offline mark count. Course responses carry `version` (1 on create, +1 per regenerate). The core schema is exported to `docs/openapi.json`, and a test fails when the export drifts.

## Entry points
- API app factory: `core/kata_core/api/app.py:11` `create_app(cfg)`. Launcher: `python -m kata_core` (`core/kata_core/__main__.py:33` runs `uvicorn.run(create_app(cfg))`).
- Worker: `python -m kata_worker` (`worker/kata_worker/__main__.py:28` `main`); reads `[worker]` and the token env var; loop in `worker/kata_worker/loop.py:61` `run_forever`.
- Core job runner: `python -m kata_core.jobs` (`core/kata_core/jobs/__main__.py:17` `main`) runs the core-side job handlers and output hooks; no service in `deploy/compose.yaml` starts it.
- Admin CLI: `python3 -m kata_core.auth.admin` (`core/kata_core/auth/admin.py:77` `main`), run with `PYTHONPATH=core`.
- DB CLI: `python3 scripts/db/kata_db.py` (`scripts/db/kata_db.py:35` `main`), run with `PYTHONPATH=core`.
- Migrate CLI: `python -m kata_core.migrate` (`core/kata_core/migrate.py:43` `main`); `--check` lists pending migrations and exits 1. Compose runs it as the `migrate` service before `core`.
- Extension: `extension/manifest.base.json` plus `extension/build/manifest.mjs` compose `dist/<browser>/manifest.json` for `chrome` and `firefox`; each `dist/<browser>/` loads `background.js`, `content.js`, `sidepanelBoot.js`, `sidepanel.html` and `bridge.js` (registered at runtime for `/c/*` course pages, `extension/src/bridgeRegister.ts`). Built by `npm run build` in `extension/`.

## Build and test commands
From `tools/gates.json` (plain commands): `.venv/bin/ruff check .`, `.venv/bin/mypy core`, `.venv/bin/python -m pytest tests -m smoke`, the full pytest run with coverage and `-m 'not flaky'`, `npm --prefix extension run build`, `npm --prefix extension run test:cov`.
Editor (from `editor/package.json`): `npm --prefix editor run build` (`tsc --noEmit`), `npm --prefix editor run test:cov` (vitest with coverage); CI runs build and `npm --prefix editor test` (`.github/workflows/ci.yml:58-60`).
The full check is `scripts/dev/check-all.sh` (the clean-clone chain, see `docs/development.md`). Its merge and full modes run the pytest, extension, editor and browser jobs concurrently; the first red job fails the run. The browser job runs its cases under xdist workers (`-n auto`, at most 4).

Lesson-check benchmark: `.venv/bin/python3 scripts/bench/lesson_check_bench.py --format markdown` with `KATA_CONFIG` and dev Postgres env set; output pasted into `docs/research/benchmarks/RESULTS.md` (`docs/research/benchmarks/RESULTS.md:29`). It refuses any embedder but `fake`.

Core tests need a reachable Postgres and `KATA_CONFIG` pointing at a config whose DB user has `CREATEDB` (`docs/api.md`, Tests).
Extension (from `extension/package.json`): `npm run build` (`tsc --noEmit`, then `build/build.mjs` runs esbuild and writes `dist/chrome/` and `dist/firefox/`), `npm test` (vitest run). Node install: TODO(verify).
E2e test: `python3 -m pytest tests/e2e` (`docs/e2e.md`). Browser tests: `scripts/dev/check-all.sh --browser` after `scripts/dev/install-browsers.sh` (`docs/e2e.md`, "Browser tests": sign-in a11y, light and dark contrast, panel layout at 360px and 320px, checked in the page body). Each `driver` case owns its profile dir, driver port and temp dir, removed at teardown; the signed-in panel test (`tests/browser/test_signed_in_panel.py`) seeds a session against a stub core on 127.0.0.1.
