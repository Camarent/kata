# Architecture

kata is a self-hosted learning companion. It keeps a per-user model of known topics and reads the open lesson page to mark new blocks. Milestone 0 ships the core API, storage, auth and the browser extension scaffold. M5 adds the trainer: course generation from concepts, progress saves and the mastery they move; and planning: syllabus import, triage against the user's mastery, study tracks with a weekly budget, and decision points. The repo holds code and docs only, no study material or personal data (`docs/design/overview.md`).

## Modules
- [config](modules/config.md) - TOML loader and env overrides; source of all settings.
- [core](modules/core.md) - Python/FastAPI HTTP API, tokens, skill-list import, job queue, concept marks, retrieval library, daily usage, per-user journal, device event ingest and message queue, policy engine, MCP server (`POST /mcp`, two read tools, egress gate), device tool in `core/kata_device/` (git pre-commit and post-commit hooks, local queue and tree-hash marker; `python -m kata_device hooks install` never overwrites a foreign hook; the `kata` entry point is not built yet), terminal tool in `core/kata_term/` (`kata term`: PTY capture of masked command lines and error kinds, JSONL spool, stdlib client; env `KATA_URL`, `KATA_TOKEN`, `KATA_TERM_MASKS`), Postgres storage, trainer (`/v1/courses`, course progress, mastery in `core/kata_core/knowledge/`, job runner `core/kata_core/jobs/runner.py`), course open link `POST /v1/courses/{id}/open` and course file serving `GET /c/{token}/{path}` (signed tokens, `core/kata_core/trainer/open_link.py`; `core/kata_core/api/routes/course_open.py:38`, `core/kata_core/api/routes/course_serve.py:55`), planning in `core/kata_core/planning/` (syllabi `/v1/syllabi`, plan `/v1/plan`, tracks and decision points `/v1/tracks`), deep health `GET /v1/health/deep` (`core/kata_core/api/routes/health.py:43`; checks DB and applied migrations, unauthenticated, booleans only), migrations CLI `core/kata_core/migrate.py` (`python -m kata_core.migrate`, `--check` lists pending and exits 1).
- [deploy](modules/deploy.md) - `deploy/`: one image `kata:local` built from `deploy/Dockerfile` (compose runs `python -m kata_core.migrate` for `migrate` and `python -m kata_core` for `core`), `deploy/compose.yaml` (migrate one-shot, then core, Postgres, Caddy on the private network), host config template `deploy/kata.host.toml`, small and large profiles in `deploy/env/`, backup, restore and relocation scripts, `deploy/provision-vm.sh`, systemd timer units in `deploy/systemd/`. Runbook: `docs/deployment.md`.
- [editor](modules/editor.md) - VS Code extension in `editor/`: posts one `editor.save` event per save (no document text), shows the server quiet mark as a diagnostic, runs the device hook installer on command.
- [extension](modules/extension.md) - MV3 browser extension: manifest, package, TypeScript sources in `extension/src/`; side panel "Open course"; content bridge that gives course pages progress load and save (`extension/src/bridge.ts`, `bridgeRegister.ts`).
- [scripts](modules/scripts.md) - `kata_db.py` CLI: create, migrate, drop databases; `scripts/bench/` lesson-check benchmark (fake embedder, three-state accuracy and abstain rate); `scripts/dev/` gate runner `check-all.sh` and pinned browser installer `install-browsers.sh`; `scripts/deploy/` checks for the VM stack (image rules, compose and config template, tombstone replay, row counts for restore).
- [tests](modules/tests.md) - pytest suites: `tests/core` (needs Postgres; includes `test_api_health.py`, `test_migrate_cli.py`), `tests/foundation`, `tests/worker`, `tests/e2e` (full lesson loop; needs Postgres and Node), `tests/browser` (real Firefox and Chrome through selenium; only `check-all.sh --browser`), `tests/scripts` (bench, install-browsers, check-all browser mode, deploy scripts: backup, restore, relocate, provision, stack, image rules, Caddyfile).
- [tools](modules/tools.md) - quality gate definitions in `tools/gates.json`.
- [worker](modules/worker.md) - Python pull loop: takes jobs of the kinds it has handlers for (`tag`, `course.generate`, `syllabus.extract`; `worker/kata_worker/handlers/`), runs them through the provider router (`worker/kata_worker/providers/router.py`), which walks the `[routing]` chain per task class over the local and Anthropic providers; cloud calls pass the policy, the secret guard and the daily cost cap; reports result, output or fail.

Reference docs: `docs/api.md` (routes, file format, CLIs), `docs/e2e.md` (end-to-end test), `docs/decisions.md`, `docs/design/overview.md`, `docs/design/extension-ui.md` (side panel and lesson page UI design, static mockups in `docs/design/extension-ui/`), `docs/INDEX.md` (generated file and symbol list).

## Data and control flow
1. Config: `load_config` reads `config/kata.example.toml`-shaped TOML (path from `KATA_CONFIG` or `--config`), applies `KATA_*` env overrides (`core/kata_core/config.py:111`).
2. Provisioning: `scripts/db/kata_db.py` calls `core/kata_core/storage/provision.py` to create databases and apply `core/migrations/*.sql`.
3. Auth: admin creates a user and an enrolment code (`core/kata_core/auth/admin.py`). Client redeems the code at `POST /auth/enrol`; the core stores only sha256 digests and returns the raw token once. Every other route takes `Authorization: Bearer`, resolved by `current_user` (`core/kata_core/api/deps.py:76`).
4. Request: route module in `core/kata_core/api/routes/` -> repository in `core/kata_core/storage/` -> Postgres. `user_id` always comes from the token.
5. Import: `POST /import` parses the skill-list text (`core/kata_core/importer/skill_list.py`) and writes topics and marks in one transaction; a bad line rejects the whole import.
6. Tagging queue: client `POST /jobs` enqueues; a worker polls `GET /jobs/next?kind=...` (204 when empty; default kind `tag`), leases a job for `lease_seconds`, and posts `result`, `output` or `fail`. Expired leases are reclaimed (`core/kata_core/jobs/queue.py`). Known/new is decided in the core from marks, not by the model.
7. Concept marks: concepts sit under a topic (`/concepts`, `core/kata_core/api/routes/concepts.py`). Each user marks a concept `known`, `learning` or `new` with optional evidence; these marks live in `concept_marks` next to the topic-level `marks` table, which is unchanged. Concept marks are private to their user.
8. Retrieval (library, no HTTP route yet): `core/kata_core/retrieval/` stores text entries (`store.py`, shared when `owner_user_id` is NULL), ranks by full-text and by cosine over embeddings, and fuses the two lists with RRF (`retriever.py`, `fusion.py`). Config `[retrieval]`; tests use the fake embedder only.
9. Lesson check: `POST /lesson-check` (`core/kata_core/api/routes/lesson_check.py:54`) returns each concept's state for the caller. A concept mark wins; otherwise the concept label is searched in retrieval and the hits decide `known`, `learning` or `abstain` (`core/kata_core/lesson_check/checker.py:40`). Thresholds in `[lesson_check]`. The check runs synchronously in the core; no worker job calls it.
10. Cost cap (worker side): `worker/kata_worker/providers/cost.py` `capped` wraps the cloud provider in the router; it checks today's spend (`GET /usage`) before each cloud call, refuses at `cap_micro_usd`, and records the cost (`POST /usage`) after it: from the token usage the API reports, with the text-length estimate only when no usage is present. The estimate with `estimate_safety_percent` is the pre-call guard only. Local calls are not capped.
11. Journal and policy (library plus read route): `core/kata_core/journal/store.py` appends and pages per-user entries (`GET /v1/journal`, `core/kata_core/api/routes/journal.py:34`). `core/kata_core/policy/engine.py` turns `error`, `ok` and `idle` events into `nudge`, `stop` and `quiet_mark` decisions in memory, from `[policy]`. Device events enter at `POST /v1/events` (`core/kata_core/api/routes/events.py:100`): each event is validated (`core/kata_core/events/envelope.py`), stored once per `event_id` (`core/kata_core/events/store.py`), and only accepted ones reach the engine. Decisions become `message` rows, delivered in that response or on `GET /v1/messages` (`core/kata_core/delivery/messages.py`).
12. MCP: `POST /mcp` (`core/kata_core/api/routes/mcp.py:26`) takes one JSON-RPC message from an `mcp`-scoped token, dispatches it in `core/kata_core/mcp/rpc.py`, and runs each tool result through `core/kata_core/mcp/gate.py` (size, secret scan, quoting) before it is returned. Details: `docs/modules/core.md` (MCP entries).
13. Trainer: `POST /v1/courses` picks concepts (gaps or named) and queues `course.generate`; the worker posts drafts to `POST /jobs/{id}/output`; the core's output hook stores them and queues `course.build`, which the core job runner builds with the external trainer command. Progress saves (`PUT /v1/courses/{id}/progress`, compare-and-swap on revision) write evidence and move concept mastery and marks. Details: `docs/modules/core.md` ("Trainer (M5)").
13a. Course open (M6): the side panel calls `POST /v1/courses/{id}/open` for a ready course and opens the returned signed `/c/<token>/index.html` URL in a tab. The course page loads its progress through the extension bridge: page stub -> `bridge.ts` -> background (`handleBridgeMessage`) -> `progressBridge.ts` -> the progress API above. Details: `docs/modules/core.md`, `docs/modules/extension.md`.
14. Planning: `POST /v1/syllabi` parses the syllabus text into modules and links each module to the user's concepts by label. `GET /v1/syllabi/...` and `GET /v1/plan` triage each module (known, partly known, new; action skip, skim, practice or learn) from the user's mastery, without writing. Tracks (`/v1/tracks`) hold ordered items and a deadline; `GET /v1/plan` allocates the weekly budget to the tracks earliest deadline first, and an open decision point holds its track's later items until the user decides it (`POST /v1/decision-points/{id}/decide`, journaled as `plan.decision`). Details: `docs/modules/core.md` ("Planning (M5)").
15. Deployment (M6): `deploy/compose.yaml` runs the `migrate` service (`python -m kata_core.migrate`) to completion, then the `core` service; Postgres is used by kata only; Caddy serves the private host name over TLS. The nightly encrypted dump (`deploy/backup.sh`, timer `deploy/systemd/`) writes a tombstone file beside it. Restore and relocation (`deploy/restore.sh`, `deploy/relocate.sh`, `--dry-run`) follow `docs/design/detailed-architecture.md` 4.3; the row-count check is `scripts/deploy/verify_counts.py`. Runbook: `docs/deployment.md`.

## Entry points
- API app factory: `core/kata_core/api/app.py:11` `create_app(cfg)`. No server launcher in repo: TODO(verify).
- Worker: `python -m kata_worker` (`worker/kata_worker/__main__.py:28` `main`); reads `[worker]` and the token env var; loop in `worker/kata_worker/loop.py:61` `run_forever`.
- Core job runner: `python -m kata_core.jobs` (`core/kata_core/jobs/__main__.py:17` `main`) runs the core-side job handlers and output hooks; launch: TODO(verify).
- Admin CLI: `python3 -m kata_core.auth.admin` (`core/kata_core/auth/admin.py:77` `main`), run with `PYTHONPATH=core`.
- DB CLI: `python3 scripts/db/kata_db.py` (`scripts/db/kata_db.py:35` `main`), run with `PYTHONPATH=core`.
- Migrate CLI: `python -m kata_core.migrate` (`core/kata_core/migrate.py:43` `main`); `--check` lists pending migrations and exits 1. Compose runs it as the `migrate` service before `core`.
- Extension: `extension/manifest.base.json` plus `extension/build/manifest.mjs` compose `dist/<browser>/manifest.json` for `chrome` and `firefox`; each `dist/<browser>/` loads `background.js`, `content.js`, `sidepanelBoot.js`, `sidepanel.html` and `bridge.js` (registered at runtime for `/c/*` course pages, `extension/src/bridgeRegister.ts`). Built by `npm run build` in `extension/`.

## Build and test commands
From `tools/gates.json` (plain commands): `.venv/bin/ruff check .`, `.venv/bin/mypy core`, `.venv/bin/python -m pytest tests -m smoke`, the full pytest run with coverage and `-m 'not flaky'`, `npm --prefix extension run build`, `npm --prefix extension run test:cov`.
Editor (from `editor/package.json`): `npm --prefix editor run build` (`tsc --noEmit`), `npm --prefix editor run test:cov` (vitest with coverage); CI runs build and `npm --prefix editor test` (`.github/workflows/ci.yml:58-60`).
The full check is `scripts/dev/check-all.sh` (the clean-clone chain, see `docs/development.md`).

Lesson-check benchmark: `.venv/bin/python3 scripts/bench/lesson_check_bench.py --format markdown` with `KATA_CONFIG` and dev Postgres env set; output pasted into `docs/research/benchmarks/RESULTS.md` (`docs/research/benchmarks/RESULTS.md:29`). It refuses any embedder but `fake`.

Core tests need a reachable Postgres and `KATA_CONFIG` pointing at a config whose DB user has `CREATEDB` (`docs/api.md`, Tests).
Extension (from `extension/package.json`): `npm run build` (`tsc --noEmit`, then `build/build.mjs` runs esbuild and writes `dist/chrome/` and `dist/firefox/`), `npm test` (vitest run). Node install: TODO(verify).
E2e test: `python3 -m pytest tests/e2e` (`docs/e2e.md`). Browser tests: `scripts/dev/check-all.sh --browser` after `scripts/dev/install-browsers.sh` (`docs/e2e.md`, "Browser tests").
